The experiment

Four popular coding-agent frameworks — Superpowers, Compound Engineering, Agent Skills, and GSD — each build the same product from the same 2,200-line specification (an issue-tracker-driven orchestration daemon), driven by the same harness and model (Claude Code + Opus 4.6), each trial in a fresh isolated sandbox. The framework is the only variable. Every artifact is then graded by two independent instruments and ranked on a weighted composite.

Building from an empty folder is only half the job. Most real agent work is fixing an issue in a codebase the agent didn't write, so the brownfield track replays real merged pull requests: the framework gets the issue as it read before the fix, and the PR's own tests, hidden until grading, decide whether it worked.

The brownfield track pilot

A merged PR that closes an issue is a ready-made task with built-in ground truth: the issue is the brief, the repo at the PR's base commit is the starting point, and the PR's tests are the oracle. The framework is still the only variable. The question is whether it helps someone produce a better PR on real code. Results are compared with the original PR that was merged upstream.

The issue as it read back then

Merged PR ↔ issue pairs are mined from the repo. Each issue is rebuilt as of the first fix commit, replaying its edit history and dropping later comments and links to the future.

A sealed repo

The workspace is rebuilt at the PR's base commit with one branch and no tags, remotes or reflog, then checked to confirm the fix isn't hiding in git history.

Hidden tests decide

A trial is resolved only if every fail-to-pass test now passes and every pass-to-pass test still does. Grading replays the framework's patch onto a clean base, offline. Edits to test files are reverted and flagged.

Harness PR vs. original PR

A blind A/B judge scores both diffs on correctness, scope, clarity, codebase fit, robustness and tests. Judge ≠ worker model. Quality is a secondary signal and never changes the verdict.

Did the framework engage?

A post-install check stops a run before spend if a framework's plugins or skills aren't visible. The session log then records which skills and commands actually ran, so plain Claude Code in a framework's clothing shows up as not engaged.

No looking up the answer

A run-owned model gateway holds the credential, so the sandbox only sees a placeholder. It refuses provider-side tools, and Docker trials can reach only the gateway. A transcript audit disqualifies any trial that reaches for the upstream fix.

Discussion as a variable

Issue threads can give the fix away. Each run picks one prompt variant (body, body+human, body+all), identical across candidates, and each item is labelled from noise up to fix_code.

Where this stands. 111 task bundles are frozen across paper-qa, xarray and zarr-python; 86 pass validation (on the tests each PR touches; full-suite validation is still open), and 106 are still marked provisional. Trials so far are a handful on paper-qa with Claude models, so treat the numbers below as a demonstration of the method, not a ranking of frameworks.

Architecture

Designed in Excalidraw (editable scene); one pipeline, every variable held fixed except the framework under test.

How grading works

PRD adherence — 40%

ViBench-style Graded Score: an evaluator agent executes a frozen, spec-derived test plan against the built, running artifact — cold-start scripts, mock services, per-step cited evidence, weighted partial credit, fatal gates. Absolute 0–100.

Code quality — 25%

A blind LLM judge scores five criteria (tests, architecture, error handling, dead code, docs), three samples each with medians, on a copy scrubbed of framework-identifying files. Judge ≠ worker model. Absolute 0–100.

Speed — 17.5%

Agent working time from the harness's own session telemetry (sandbox setup excluded), min-max normalized within the run: fastest 100, slowest 0.

Token spend — 17.5%

Total session cost from harness telemetry, normalized the same way. Together with speed: the efficiency frontier.

These weights apply to the spec-building track. The brownfield track reports hidden-test resolution first, with quality against the original PR, cost and agent time beside it.

Fairness engineering

Identical rendered prompts for every candidate · version-pinned frameworks with post-install asserts · frozen content-hashed PRD and test plan · blind judging on marker-scrubbed workspaces · per-trial sandbox isolation with contamination tests · evaluators forbidden from repairing artifacts · evidence cited for every verdict · budget caps with explicit capped status, never silent truncation · rankings with overlapping variance flagged inconclusive. On brownfield tasks: byte-identical prompts with no PR references · credentials held outside the sandbox · fresh home and config per trial, with no operator plugins, memory or instructions · grading from a clean base · disqualification for reaching for the upstream fix.

Pluggable by design

Five isolation providers behind one interface (Daytona, E2B, Docker, Apple-Silicon micro-VMs, git worktrees) all running one pinned trial image. Eval targets are swappable — bring your own PRD with a frozen test plan and the same machinery grades it. Next up: pluggable worker models (GLM, Kimi, Qwen via Anthropic-compatible endpoints) and alternative harnesses (OpenCode, Codex).

Run it yourself

git clone https://github.com/natea/harness-eval && cd harness-eval
bun install && cp .env.example .env
bun run src/cli.ts run --candidates superpowers --trials 1 --provider docker
bun scripts/grade-trial.ts runs/<run-dir> superpowers-t1
bun run dashboard   # full interactive dashboard on localhost

# brownfield: replay a real PR (real spend; needs a local clone of the repo)
bun run src/cli.ts run --brownfield Future-House/paper-qa --tasks pr293-issue292 \
  --variant body --candidates bare --provider docker \
  --worker-model claude-sonnet-4-6 --judge claude-opus-4-6 --clone ../paper-qa
