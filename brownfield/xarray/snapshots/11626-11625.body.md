# isel with an empty list fails on multi-dimensional variables for h5netcdf and scipy backends

_Opened by @aniruddhaadak80 on 2026-09-28_

### What happened?

`isel` with an empty list raises an error instead of returning an empty array when the
target variable has more than one dimension and the `h5netcdf` or `scipy` engine is used.

Both of those engines declare `IndexingSupport.OUTER_1VECTOR`. In
`xarray/core/indexing.py`, `_decompose_outer_indexer()` converts an empty indexer array
into an empty slice `slice(0, 0)` for the backend, but it does not append a matching
entry to the in-memory (`np_indexer`) half of the decomposed key:

```python
if isinstance(k, np.ndarray) and k.size == 0:
    # empty np.ndarray key is converted to empty slice
    # see https://github.com/pydata/xarray/issues/10867
    backend_indexer.append(slice(0, 0))
```

An empty slice keeps the dimension, unlike an integer key (which legitimately drops it and
correctly gets no `np_indexer` entry). So the returned `np_indexer` tuple ends up one
element shorter than the number of axes of the array the backend loaded. Applying it then
indexes the wrong axes and raises `IndexError` (or, for higher-dimensional variables,
`ValueError: zip() argument 2 is longer than argument 1`).

The 1-D case is unaffected: there the resulting `np_indexer` is an empty tuple, which
`explicit_indexing_adapter` skips entirely. That is why the existing regression test
`test_empty_isel` (which only uses a 1-D variable) does not catch this.

### What did you expect to happen?

`on_disk.isel(x=[], y=[1, 3])` should return the same thing as the equivalent in-memory
operation, i.e. an array of shape `(0, 2)`.

### Minimal Complete Verifiable Example

```python
import numpy as np

import xarray as xr

path = "repro.nc"

in_memory = xr.Dataset(
    {"v": (("x", "y"), np.arange(20.0).reshape(4, 5))},
    coords={"x": np.arange(4), "y": np.arange(5)},
)
in_memory.to_netcdf(path, engine="scipy")

on_disk = xr.open_dataset(path, engine="scipy")

expected = in_memory.isel(x=[], y=[1, 3])
print(expected["v"].values, expected["v"].shape)  # [] (0, 2)

actual = on_disk.isel(x=[], y=[1, 3])
print(actual["v"].values)  # raises
```

### Steps to reproduce

1. Write a 2-D (or higher-dimensional) variable to a netCDF3 file and reopen it with
   `engine="scipy"` (or `engine="h5netcdf"`).
2. Call `.isel(...)` with an empty list on one dimension and a non-trivial selection on
   another.
3. Read `.values` (or `.load()`), which triggers the lazy backend read and raises.

### Anything else we need to know?

Enumerating all combinations of `{empty array, integer array, slice}` per axis and
comparing `decompose_indexer()` against direct outer indexing on the current `main`
(`bb652ffe`) gives the following for a 2-D `(4, 5)` and a 3-D `(4, 5, 6)` array:

| `IndexingSupport` | engines | 2-D | 3-D |
| --- | --- | --- | --- |
| `OUTER` | netCDF4 | 9/9 pass | 27/27 pass |
| `OUTER_1VECTOR` | h5netcdf, scipy | 8/9 pass | 20/27 pass |
| `BASIC` | pydap | 4/9 pass | 8/27 pass |

The `BASIC` branch calls `np.min(k)` on the empty array and raises
`ValueError: zero-size array to reduction operation minimum which has no identity`; that is
the behaviour reported in #9075. All failures are hard errors; none of the affected
combinations silently returns wrong data. This report is about the `OUTER_1VECTOR` branch,
which fails differently and remains unfixed.
