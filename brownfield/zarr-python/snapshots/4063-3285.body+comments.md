# unified runtime type checking for our json data

_Opened by @d-v-b on 2025-07-23_

Labels: help wanted, good-first-issue

Reading array metadata documents means consuming JSON-formatted data and type-checking them. We are doing this in a clunky way right now: for each field `f`, we essentially have a `parse_f` function that checks if the input data is compatible with `f`. 

A big improvement would be unifying the `parse_x` functions into something with the following form:

```python
def check_literal(value, type_annotation) -> type_annotation:
    if value in get_args(type_annotation):
        return value
    raise UsefulException

def parse_union(value, type_annotation) -> type_annotation:
    # check if the value is in the union type, return it if so

def parse_tuple(value, type_annotation) -> type_annotation:
    # check if the value is consistent with the tuple type annotation, return the input as a tuple if so

...

parse_json(value, type_annotation) -> type_annotation:
    # categorize the type annotation into Mapping, tuple, Sequence, union, literal, and call out to the relevant 
    # parsing routine
    # return data 
```

i.e., functions that take a value and a type annotation, and return data assignable to that type annotation or raise a useful exception. In my thinking these are not strict type checks, because these functions are allowed to transform the input, e.g. `parse_tuple([1,2,3], tuple[int, int, int])` would return `(1,2,3)`.

This would remove a _lot_ of redundant code. We would keep the scope narrow by only concerning ourselves with the types relevant for creating array metadata documents, namely:

- primitive types None, str, int, float, bool
- Sequences (they should come out as tuples)
- unions
- TypedDict (essential for handling JSON form of dtypes, codecs, chunk grids, and metadata itself)
- Mapping[str, T], where T is any of the other types in this list

I have have had LLMs whip up implementations of this on like 3 separate occasions, and each time it wasn't more than a few hundred LOC, so I think this would not be a huge maintenance burden.

**@d-v-b** (2025-08-23):

an update on this: I have been working on an implementation of a runtime type checker that basically works for zarr, in the sense that, for some JSON-like type `type`, the function `check_type(obj, type)` will check if `obj` is assignable to `type`. The code is pretty hideous because python type annotations were not really designed for runtime use, and it shows.

So that's one feasible solution -- a function that introspects a type, breaks the type and the value into parts as needed, and aggregates the type checking results of those sub-types and sub-values. 

An advantage of this approach is flexibility -- we can support user-defined types very easily. The disadvantage is runtime cost and ultimately inefficiency -- given a type like ` Movie = TypedDict('Movie', {'name': str, 'year': int})`, each time we call `check_type(obj, Movie)`, we spend cycles introspecting the `Movie` type. 

An alternative is to use code that takes a type `T` and _generates the source code for a type-checking function for T_. Then we could insert these functions in our source code like any other function.

To keep our codebase fully human-written, I am imagining introducing the auto-generated type checking functions in our test suite. A test will check if, for each type we want to check (like all the metadata types), there is a function with source code matching exactly the result of the auto-generated type checker  for that type. if not, the test fails, and the developer is prompted to generate that missing function. because this code generation is part of our test suite, it's easy to modify by simply telling pytest not to check certain types, for example.

This might be a totally weird idea that i'm not explaining properly. please let me know if this is confusing, or if there's some flaw here. I'm going to keep going with the runtime type checking function and open a PR soon, but I will have this code generation idea in the back of my mind as an alternative if we ever start to experience performance problems.
